# `~/AGENTS.md` should ban harness memory stores outright, not call them a staging area

## Context

Filed from an `agent-skills` session, 2026-08-29, into the store because that session did not own
this repo's tree.

The current "Claude Code's auto-memory" section says the per-project memory directory "is a staging
area only, never a durable store — it's siloed per project directory, so anything left there is
invisible to every other repo's sessions", and tells the reader to migrate anything durable out and
delete the entry.

**That wording is too weak, and it was read as permission.** Same day, in this session: asked to
file a next-session handoff "somewhere durable", an agent reasoned that the objection was about
durable _knowledge_ being siloed, that a perishable per-project handoff was exactly what a staging
area is for, and wrote one into `~/.claude/projects/<encoded path>/memory/` with a new `MEMORY.md`
index. It even flagged the tension explicitly and proceeded anyway, because the rule as written
appeared to allow it.

[DECISION: **no memories, for any harness, for any project, for any reason.** Stated by the user
2026-08-29 on seeing that entry: project data and user-wide practices are not to be vendor-locked,
and cross-harness portability is the reason. The carve-out is harness **configuration** —
`settings.json`, hooks, keybindings, statusline — which is expected to differ per harness because it
describes the tool rather than the work.

The distinction that makes it easy to apply: configuration describes _the harness_, and is fine to
keep in that harness's own format. Anything describing _the work_ — what a repo is for, what was
decided, what is left to do — has to be a plain file any agent can read.]

[PITFALL: the failure was not that the rule was missing, it was that the rule explained a
_mechanism_ ("siloed", "not durable") instead of stating a _prohibition_. An agent that accepts the
mechanism argument can then reason its way to an exception — "this content is deliberately
perishable, so siloing is the point" — and that is exactly what happened. A rule whose reasoning can
be turned around is not a constraint.]

## Design

1. **Rewrite the section as a flat prohibition**, with the config carve-out stated in the same
   breath so it does not read as absolutism about all harness state. Keep it short — this is an
   always-loaded file.
2. **State the sorting rule, not the mechanism.** "Configuration describes the harness; anything
   describing the work is a plain file" is one line and is what an agent actually needs to route by.
3. **Point at where the work goes instead**, which the file already covers under "Agent instructions
   & knowledge": repo-specific durable knowledge to that repo's `AGENTS.md`, cross-repo preference
   to `~/AGENTS.md`, anything plan-shaped to `plans/` per `plan-docs`. A prohibition with no
   destination is what produces the next workaround.
4. **Do not name the destination as Claude-Code-specific.** The current heading sits under a "Claude
   Code specifics" section, which is part of why it reads as a note about one vendor's feature
   rather than a general rule. It belongs with the durable-knowledge rules.

Edit the fragment in `config/agents-md/`, never the deployed file, then
`inv deploy.all --name agents-md`.

## Files touched

- `config/agents-md/` — the fragment owning the auto-memory section, moved out of the Claude Code
  specifics block and into the knowledge-routing one.
- `~/AGENTS.md` / `~/.claude/CLAUDE.md` — regenerated by the deploy task, never edited directly.

## Verification

Behavioural: a later session asked to persist something across sessions should reach for a plan file
or an `AGENTS.md`, not a harness store. Until one does, the only evidence is the single occurrence
above.
